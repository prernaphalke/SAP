System Conversion (Brownfield Approach) is like renovating an old house. Instead of building a new house from scratch, you start with your existing house and make improvements.

In this case, you take your current SAP ERP system and convert it to SAP S/4HANA Cloud Private Edition or on-premise. You use your existing system as a template, making it as similar as possible to the new system. Once the conversion is done, you can start making any necessary adjustments based on your project needs. The main goal is to ensure the core system is clean and efficient.

----------------------------------------------------------------------------------------
_-------------------------------------------------------------------------------------------------

 

**New Implementation (Greenfield Approach)** is like building a brand-new house on an empty plot of land. You start fresh without using any parts of an old house.

In this case, you create a new SAP S/4HANA system (Cloud Public Edition, Cloud Private Edition, or on-premise) from scratch. This new system doesn't carry over any old custom code or modifications from your previous SAP ERP system. Because of this, you don't need to worry about fixing or adapting old changes.

The new system starts with a clean core, meaning it's free from any old clutter. While you might still need to add new extensions based on the SAP S/4HANA Cloud extensibility model, the overall migration project is simpler because there's no conversion work needed.

Instead of launching the new system all at once (a "big bang" approach), you can roll it out in phases, such as by different company codes. The main goal is to keep the core system clean and efficient from the start.

This workstream involves different ways customers have modified their SAP systems over the years.

**Modifications** can be:
1. **Direct**: Changes made directly to an SAP object, either following SAP's instructions (SAP Note) or to change how an object behaves.
2. **Indirect**: Changes that include:
   - **Clones**: Copies of SAP objects.
   - **Implicit Enhancements**: Additions at the beginning or end of code.
   - **Class-Method Overwrites**: Changing methods in classes.

**Tools** like transaction codes **SPDD** and **SPAU** (or **SPAU_ENH**), and a clone finder tool, help identify these modifications.

The goal is to have a **clean core** with no modifications. The project team should aim to remove these modifications. They usually find that modifications are:
1. **Obsolete**: Identical to an SAP version.
2. **Unused**: Not used according to usage statistics.
3. **Irrelevant**: Not needed in SAP S/4HANA.
4. **Replaceable**: Can be redesigned as in-app extensions.

If a modification is essential for business and can't be redesigned, the customer should contact SAP for guidance.

### Cloud Computing Principles

1. **Elasticity**:
   - Think of it like a rubber band that can stretch and shrink. Cloud resources can expand or contract based on your needs. For example, during payroll processing, you might need more resources, and the cloud can provide that flexibility.

2. **Pricing**:
   - Cloud services are like a utility bill. You pay based on how much you use. Different providers offer different pricing plans, like subscription-based or pay-as-you-go.

3. **Availability**:
   - This is about how often you can access cloud resources. For example, if you need resources for payroll twice a month, the cloud ensures they are available when needed. Many providers offer 24/7 availability, so you can access resources anytime.

4. **Service Level Agreement (SLA)**:
   - SLAs are like a guarantee from the provider. They promise a certain level of service, like 99.99% uptime. This means the system might be down for only a few minutes each month.

### Is There a Difference?

- **Cloud vs. Data Center**:
  - Cloud computing is different from having your own data center. In the cloud, your applications should work regardless of the underlying infrastructure (servers, OS, etc.). This means you don't have to worry about compatibility issues if the cloud provider changes their setup or if you switch providers.

- **Cloud Native**:
  - To make the most of the cloud, applications need to be designed specifically for it. This involves rethinking how we develop and maintain software, leading to the concept of "cloud native" applications.

In simple terms, cloud computing offers flexibility, cost-effectiveness, and reliability, but it requires a new approach to developing and managing applications.

### Cloud Native Approach

1. **Infrastructure Independent**:
   - Cloud native applications work the same no matter what infrastructure (servers, networks, etc.) the cloud provider uses. This means you don't have to worry about the specific hardware or software the provider uses.

2. **Microservices**:
   - Applications are broken down into smaller, independent pieces called microservices. Each piece handles a specific function and can be developed, deployed, and maintained separately. For example, a banking app might have separate microservices for user interface, data storage, and transaction processing.

3. **Application Programming Interfaces (APIs)**:
   - APIs are like messengers that allow different software components to communicate with each other. For example, a banking app uses APIs to check your account balance or transfer money. APIs follow certain rules and protocols to ensure smooth communication.

### REST (Representational State Transfer)

1. **Resource**:
   - In REST, a resource is any piece of information, like a bank account. Each resource has a state (e.g., the current balance) that can change over time.

2. **Client-Server**:
   - The client (e.g., your banking app) and the server (where the API is hosted) are separate. They communicate over the internet.

3. **Stateless**:
   - Each request from the client to the server is independent. The server doesn't remember previous requests. For example, if you check your balance twice, each request is treated separately.

4. **Cacheable**:
   - Some data can be stored temporarily to speed up responses. For example, your account balance might be cached to provide quicker access.

5. **Layered System**:
   - There can be intermediary systems (like load balancers) between the client and server to improve performance and security.

6. **Code on Demand** (Optional):
   - Servers can send executable code (like JavaScript) to the client to enhance functionality.

### CRUD Operations with REST

- **Create**: Use HTTP POST to add new data.
- **Read**: Use HTTP GET to retrieve data.
- **Update**: Use HTTP PUT to modify existing data.
- **Delete**: Use HTTP DELETE to remove data.

In summary, cloud native applications are designed to be flexible and independent of the underlying infrastructure. They use microservices and APIs to ensure smooth communication and adaptability. REST APIs follow specific principles to manage resources efficiently and support modern application needs.

### From ABAP Classic to ABAP Cloud

1. **Need for Flexibility**:
   - Companies need applications that can quickly adapt to changing customer demands. SAP S/4HANA Cloud helps with this by allowing flexible and easy-to-update applications.

2. **Evolution of ABAP**:
   - ABAP, a programming language used by SAP, has evolved over time. Initially, it was used for reports, then for creating programs and extensions. Now, with cloud computing, ABAP has evolved again to support cloud-native development.

3. **Cloud Native and REST APIs**:
   - Cloud native means developing applications specifically for the cloud. REST APIs are a key part of this, allowing different parts of an application to communicate over the internet.

### ABAP Cloud Development Model

1. **Cloud Native ABAP**:
   - ABAP has been optimized for cloud development. This means it can efficiently create and manage applications in the cloud.

2. **Programming Models**:
   - **Transactional (OLTP)**: Build business objects and expose them as services (e.g., Sales Order).
   - **Analytical (OLAP)**: Create services and UIs for data analysis (e.g., integrating with SAP Analytics Cloud).
   - **Integration**: Strong data and application integration for service-oriented environments.

3. **Key Features**:
   - **Reuse Services**: Use core business services like number ranges and application jobs.
   - **Built-in Qualities**: Ensure scalability, upgrade stability, and extensibility.

### Evolution to ABAP Cloud

1. **Innovations**:
   - Over the past decade, several innovations like ABAP development tools for Eclipse, Core Data Services, and the ABAP RESTful application programming model have been introduced. These innovations together form the ABAP Cloud.

2. **Availability**:
   - ABAP Cloud is available in SAP BTP, ABAP environment, and SAP S/4HANA Cloud Public Edition. It coexists with ABAP Classic in SAP S/4HANA Cloud Private Edition and SAP S/4HANA.

### Differences Between Classic ABAP and ABAP for Cloud Development

1. **Subset of Features**:
   - Not all ABAP features are compatible with cloud-native needs. Only a subset is used in ABAP Cloud. For example, obsolete keywords and certain UI technologies are not used.

2. **Language Version Assignment**:
   - Developers must assign a language version to development objects to ensure they are ABAP Cloud compliant.
